## 1. 结论

本次可确认的触发原因是 HTTP 请求体大小超限，原始错误为：

```text
413 Failed to buffer the request body: length limit exceeded
```

不是已证实的 1M token 容量耗尽。最后一个正常请求的服务端输入用量是 160,316 token（包含缓存命中部分），首次失败的本地用量估计为 169,879。没有观察到该区间发生正常的 autocompact。

故障发生时，恢复路径把请求体超限当作上下文超限；流式失败后先重发未缩减的消息，随后才进行激进压缩。成功的压缩结果只服务于当前请求，没有更新后续请求的会话视图。因此下一步重新发送大历史，再次进入同一恢复路径。界面将两种不同阶段的事件都显示成 attempt 1/2。

## 3. 修复前实现的设计问题

### P1：恢复错误分类混合了不同资源限制

`zapsdk/core/errors.ts:42` 的 `isLikelyContextLimitErrorMessage()` 将 413、request too large、400 + json、unexpected end of、请求解析失败等都纳入上下文溢出。

结果：传输体积、序列化错误和 token 超限共用同一套有损恢复。当前会话是已确认的 413；其他解析错误的误分类通过离线输入验证，不能混称为本次会话发生过的错误。

应分别处理 `context_token_limit`、`request_body_limit`、`invalid_request`、`image_unsupported`、`transient_transport` 和 `unknown`。优先消费 provider 的结构化状态/错误码，文本匹配只作为保守后备。只有明确的 token 超限才进入语义压缩。

### P1：只有 token 预算和单文件大小检查，没有整个请求的字节预算

`zapsdk/utils/image.ts` 仅限制单图 20 MiB；普通 PNG 不做缩放或重编码。`zapsdk/core/providers/openai-compatible.ts:620` 重放历史图片 Base64。`zapsdk/context/token-counter.ts:61` 对每张图片固定加 765 token。

token 数和传输字节数是独立维度，不能通过降低 1M 的上下文阈值解决几十 MiB 图片重放。即使 token 估算准确，也不能预测请求体的硬限制。

需要独立记录序列化后的 UTF-8 字节、图片字节/数量、文本与 schema token，以及单图约束。未获得上游请求体上限时明确记为未知；不能伪造固定通用上限。

### P1：成功恢复没有形成后续请求可复用的状态

`zapsdk/context/reactive-compact.ts:59` 在局部 `currentMessages` 中压缩，只返回 response 和 compacted 布尔值。`zapsdk/agent/loop.ts:2083` 只接收 response；与有 replaceMessages 回写的外层压缩路径不一致。

本次日志证实：当次实际输入约 20K，下一步的会话估计仍约 170K，继续重放旧历史。这是长期循环的主要原因。

需要区分原始审计历史与可发送上下文，提交版本化的恢复变更：媒体缩减更新后续请求视图，语义摘要更新有效会话上下文。恢复不能把 transient memory/todo 注入错误地写成永久用户消息，也不能覆盖恢复期间到达的新输入。

### P1：已知失败的请求被原样重发；没有“有效缩减”门槛

流式请求失败后，`loop.ts:2071` 调用 `callWithCompaction()`；后者首先执行 provider.call，失败后才压缩。于是一个逻辑步骤出现“大请求失败 → 大请求再次失败 → 缩减请求成功”。

`callWithCompaction()` 不检查 compactMessages 的 compacted 返回值；未缩减的请求也会重试。独立离线复现：只有 system + 短 user 两条消息、每次返回 413，最终仍调用 provider 3 次，发送两条压缩提示。

应将已知错误交给同一个恢复控制器，先产生修复候选、验证受限维度严格下降，再允许下一请求。同一个请求摘要值和同一错误不能重复发送；重试次数属于一个恢复周期，不能在 stream→call、外层/内层恢复切换时重新计数。已有工具副作用和已交付内容仍不得重放。

### P1：为解决图片体积而过度删除文本历史

ReactiveCompact 先微压缩旧工具结果，再截断大文本，再保留前导 system 和最后 6 条消息；中间范围仅保留边缘消息预览，不是完整语义摘要。Microcompact 保留最近 2 条工具结果，既没有按图片总量决定，也没有按任务依赖决定。

本次恢复把实际输入从约 160K 压到约 20K，远超“减少历史图片传输”所需的文本损失。恢复后模型曾围绕“07 是否存在”发出新的选择问题，尚未完成视频交付；只能说这与上下文丢失风险一致，不能仅凭相邻时间关系证明该回复完全由压缩造成。

应优先对旧媒体生成可重取引用、保留已有文字观察和来源；必要时调整预览尺寸。活跃视觉任务所需图片应有保留规则，不能一律删光。只有 token 压力实际达到阈值才进行语义摘要，且保留用户目标、约束、授权边界、待办、未完成工具组及产物验证状态。

### P2：压缩结果判定缺少多模态度量

`ReactiveCompact.compactMessages()` 用消息条数和 message.content 字符数判断是否缩减，不统计 contentBlocks 的实际负载。图片删除可能大幅降低字节却不降低文本字符；加入“图片已省略”标记还可能增大文本。

结果契约应返回每个维度的 before/after、具体变更、保留引用与无进展原因；不要用一个布尔值代表 token、字节和语义效果。

### P2：多条压缩路径缺少统一契约

- 回合前 `ConversationManager.compress()` 按 token 保留尾部 Turn。
- 回合中 `AutoCompact` 同时按消息数和字符预算选择尾部，默认最多保留 10 条消息。
- 异常恢复 `ReactiveCompact` 使用固定 6 条尾部消息和边缘预览。
- 回合前历史预览只拼 role/content；AutoCompact 的预览还包含 tool call 参数。相同会话在不同入口可能得到不同的摘要证据。
- 回合前阈值包含 prompt overhead；回合中的 soft trigger 主要看 conversation 估计；完整请求预算又在发送前单独核算。

这不代表每条路径都失效，但会导致触发口径、证据保留、质量校验和状态提交不一致。应共享 RequestPlan 和 RecoveryResult，策略可以不同，度量、提交、取消与持久化契约必须一致。

### P2：提示混淆阶段，usage 缺少请求版本关联

`wireRunHandlers.ts:567` 将缺少 attempt 的 reactive_compact 事件也默认渲染成 attempt 1/2；实际压缩事件再次显示同样内容。日志里的原始 413 未显示在提示中。

失败请求的 usage 明确标为未报告，不能按 0 token 解读。恢复后的真实 usage 对应缩减请求，而本地估计仍对应旧会话；没有 requestId/contextRevision 绑定时，UI 容易把两个不同上下文的数据放在一起比较。

需要一次恢复一条可更新状态：失败原因 → 变更与缩减量 → 重试 → 成功/失败。恢复成功后展示实际保留量；保留完整审计详情供诊断，不重复刷屏。

## 4. 建议的共享架构

```text
不可变原始会话 / 媒体资源
    ↓ 有效上下文版本 + 当前任务保留项 + 临时上下文
RequestPlanner
    ↓ 按实际 provider 格式序列化并度量
RequestBudget { tokenLimit, inputLimit, outputReserve, bodyBytesLimit, imageLimits }
    ↓
发送一次请求
    ├─ 成功：usage 与 requestId / contextRevision 绑定
    └─ 失败：结构化分类 → RecoveryController
          ├─ token 超限：保留关键状态的语义摘要
          ├─ body 超限：媒体/附件传输缩减
          ├─ 请求格式错误：明确诊断，不删除对话
          └─ 其他错误：各自策略
              ↓
          受限维度确有改善 + 工具协议完整 + 无副作用重放
              ↓
          请求重试成功后提交新上下文版本，供下一步及会话恢复使用
```

原始证据留存和有效上下文是两个不同视图。无需把所有原始图片永久重发，也无需为了缩小 HTTP body 丢掉用户目标。旧媒体引用必须包含来源和内容版本，不能在文件改变后悄悄换成另一张图。

## 5. 实施顺序与验收

1. **先修恢复闭环**：分类 413 与 token 超限；移除原样重发；统一恢复 ID/次数；提交成功候选；无进展立即停止自动重试。两次连续模型步骤中，只允许第一次发生一次受控恢复，第二次不得重发旧大请求。
2. **补请求与媒体预算**：按 provider 序列化后测 UTF-8 字节，支持媒体引用/预览与任务保留策略。构造“低于 token 阈值但超过字节上限”的多图会话，只缩减媒体传输，保留文本任务状态。
3. **统一压缩状态与观测**：共享保留项、质量检查、版本提交、重启恢复及 UI 状态。验证修复不破坏工具调用配对、临时上下文、用户新输入、授权语义、取消行为与已有副作用保护。

必须新增的回归场景：

- 1M 配置、约 160K 输入、连续 30 张图：模拟 413，下一步持续使用已恢复视图。
- 真实 token 超限与 request body 超限走不同策略；普通 400 JSON 错误不触发语义摘要。
- 压缩无变化：不重试完全相同的请求；展示真实阻塞原因。
- 图片被移除但文本标记增大：仍正确识别 body 字节缩减。
- 恢复时取消/新输入/工具已执行：不会回滚新输入或重复执行工具。
- 重启后有效上下文保持缩减，原始图像证据仍可定位。
- 恢复前后保留原任务与未完成验证，避免把最近闲聊或局部问题当成全部目标。
- 同一次恢复只有一条状态，准确区分尝试、已完成和失败，不把未知 usage 显示为真实零用量。

## 7. 故障链修复与验收

已实现：

- `request-recovery.ts` 统一区分 token 与 body 限制。普通 JSON 解析错误不再触发压缩。
- 已失败的流式请求直接生成缩减候选，不再先原样调用一次非流式 API。候选必须改善受限维度，并且不能重复已失败的候选；恢复耗尽后不会重新进入外层恢复或备用 provider。
- 413 按累计图片字节缩减较早的工具图片，只替换媒体块，保留全部文字、用户附件及最近一组工具图片。省略项保留来源和 Base64 内容摘要；本地原始图片不变。
- 成功恢复后、执行返回的工具之前，提交有效会话视图；后续工具步骤和下一用户回合复用。提交前验证会话版本，拒绝覆盖恢复期间的新输入。临时上下文单独处理，相同内容的缩减可复用，变化的 live delta 仍实时刷新。
- 重试重新计算 token 预算并获得独立请求 ID；取消和共享截止时间优先于自动恢复。UI 在同一行更新原因、进度和结果，移除无真实 attempt 的重复提示。
- OpenAI-compatible / Anthropic 在 SDK 传输前测量最终参数 JSON 的 UTF-8 字节与指纹，完成/失败事件写入结构化日志；不记录整个请求体。
- provider 支持可选 `maxRequestBytes`（config.json 对应 provider 字段，以及 SDK provider options）。只设置明确已知的上限；默认不猜测。配置了上限时，在传输前检查，超限走同一条媒体恢复路径。它不会更改模型 contextWindow。

## 8. 独立审查后的修正

对 `6f736de1` 分别进行恢复状态机、provider 传输与终端状态审查，发现四项可复现缺陷：

1. **P1：缩短历史后，临时上下文可能拆开工具组。** 原插入索引沿用 run 开始时的消息数量；14 条历史缩成 7 条后，连续工具步骤会把临时 user 消息插在 assistant/tool_result 之间。改用独立上下文锚点，并在恢复和消息重建后重定位；重试也保留临时消息的相对顺序。连续 6 个工具步骤验证配对完整。
2. **P2：使用完整历史恢复较小请求视图，误判无进展。** 失败请求只有 18 张图，完整历史却有 100 张。现仅缩减实际失败请求，再把改动合并回完整历史；未发送的 82 组图片保持原样。进程内保留请求视图起点，避免缩减释放 token 预算后旧图片重新进入请求。离线复现从 299,464 字节降至 155,185 字节，下一步骤及下一回合不回流。
3. **P2：错误文本中的数字 413 被误当 HTTP 状态。** `Unexpected token x in JSON at position 413` 会触发图片删减。改为仅匹配结构化状态或明确 HTTP/body-limit 语义；解析错误直接保留原错，不重试或提交缩减。
