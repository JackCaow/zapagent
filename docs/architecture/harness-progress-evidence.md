# 通用 Harness 进展与完成证据

> 完成语义的设计修订见 [41. Agent 运行结果与任务验收架构重设计](41-agent-outcome-and-acceptance.md)。本文下方“只有显式合约触发交付判断”描述原设计意图；基线 V2 factory 实际默认注入 `delivery-response-v2`，详见第 40 篇。M1 新入口已按 [第 42 篇](42-agent-outcome-implementation-contract.md) 分离执行与验收；旧门禁保留在 legacy 路径。

本次修复作用于共享 SDK 和 Host 投影。它不依赖任务名、题库、隐藏断言或模型型号。

## Shell 执行事实

`bash` 是兼容工具名，解释器由执行后端决定。本机 Unix 使用 `/bin/sh -c`，Windows
使用 `ComSpec`（缺省 `cmd.exe`）及 `/d /s /c` 参数；登录终端的 `SHELL` 或
`PSModulePath` 不决定命令实际使用的语法。普通进程与 OS sandbox 共用
`localExecutionShell`，默认/自定义提示词和工具描述使用同一事实。

远程或自定义后端通过 `ExecutionEnvironmentFacts.shell` 提供自己的解释器事实，
App 同时将其传入主 Agent、子 Agent 的工具描述。SDK 直接装配工具时可用
`ExecuteCommandOptions.executionShell` 描述自定义 broker 的解释器；该字段只是元数据，
不能更换执行器、绕过权限或改变 VM 协议。未指定时描述本机解释器。

此修复消除提示与实际执行不一致，不自动改写命令、安装工具或保证模型选择正确语法。
shell 管道和复合命令仍保留各平台原有退出码语义；命令零退出码不能证明检查通过。

## 进展观察

`ToolProgressTracker` 分开记录执行成功、未验证的工作区修改、新证据和明确检查结果。
成功写入或任意 shell 的零退出码不重置停滞计数；新的只读结果和诊断可以重置。
相同观察只计一次；摘要历史最多保留 256 项。目录指纹或缺少内容 hash 的写入保持
保守的“未验证修改”状态。todo 等已声明仅修改 Runtime 状态的工具不会被计作文件修改。

连续三轮没有新证据时，V2 发出一次切换方法/获取新诊断的建议；同一停滞期间不重复
追加该提示。native 和 XML 工具路径采用相同计数。提示本身不强制终止任务。

## 时间预算

请求生命周期事件附带每次流式请求独立的输出统计：首次思考、可见文本、工具协议输出
距请求开始的耗时，以及对应文本和工具参数的字符数。统计只随已有生命周期事件发出
快照，不保存正文、不增加逐 token 事件，也不进入模型提示或会话历史。失败和取消保留
已观察统计，重试从零开始；非流式请求不宣称流式统计。字符数采用 JavaScript 字符串
长度，不等于 token 或字节数；工具协议出现不证明工具已经执行，耗时也不是模型 CPU
时间。这些观察用于区分长推理与缺少输出，不改变现有超时、重试和预算决策。

工具执行的绝对截止时间在授权入口、排队后的执行准入、检查点完成后和后端就绪后重新检查。
定时器可能因宿主机睡眠或事件循环繁忙而延迟，不能单独证明此时仍允许启动 handler。
已过期的时间保持为过去的时间点，不随下一次工具调用刷新；执行器与 broker 的等待定时器
取工具自身超时和调用上下文截止时间中更早的边界。拒绝的新调用报告 `DEADLINE_EXCEEDED`，
不调用工具 handler。该机制不抢占已开始的同步代码，也不替代进程隔离或 provider 重试的预算检查。

Provider 调用另携带同一时钟域的绝对准入截止时间。重试开始前、退避后、fallback 和
压缩后的重新请求均检查剩余期限；自动摘要及摘要修复共享运行预算，最终总结使用实际
剩余收尾窗口。截止时间到达后的拒绝属于终止性的取消，不作为可重试的网络超时。
定时器继续负责取消进行中的 I/O，绝对时间检查负责防止定时器延迟时启动新请求。
该元数据不进入模型提示；继承的工具截止时间不改变无运行预算时纯文本汇报的既有语义。

`converge` 允许短修复和针对性验证。`finalize` 以实际收尾预留时间为边界，不再以
剩余 20% 判断。预留取配置下限与最近八次成功的强制收尾调用最大耗时的 1.25 倍加取消余量的较大值。
余量最多 250ms，短预算按配置下限的 25% 缩放，避免固定余量占满整个运行窗口。
模型提示、步骤准入和取消采用相同边界。最终回答调用最多使用实际剩余时间，不能
在截止时间之后再获得一份完整收尾预算。异步完成检查也接受取消信号。

强制收尾超时、失败、没有剩余时间，或清理工具协议文本后没有可见总结时，返回包含停止原因和
“任务完成情况未验证”的确定性说明。历史 assistant 文本可能早于后续修改或失败检查，不能
直接提升为当前最终结论；原历史和工具结果保留供继续执行。正常生成的总结、用户取消和
执行停止原因沿用原有语义，收尾说明不代替外部验收。

## 逐步检查

bash 可选 `check_steps`；每步在 `cwd` 的新 shell 中执行，失败后停止，全部步骤共享
一次前台超时预算。示例：

```json
{
  "check_steps": ["bun run build", "bun test"]
}
```

可以省略 `command`，参数校验会在权限判定和审批之前生成完整命令，审批与执行使用相同参数。
同时提供 `command` 时必须匹配完整的 `(step) && (step)` 列表；不匹配时拒绝执行。
权限、危险命令检查和沙箱排除逐步检查真实命令；不支持后台检查。
步骤内仍是普通 shell 语义，须自行传播错误，不能用 `; echo done` 掩盖失败。
普通 shell 的 `success` 含义保持兼容；`runtime.command` 记录实际退出码，
`runtime.verification` 只报告明确检查的观察结果，不等于整个任务或外部 verifier 已通过。
这些事实会进入 Headless JSON/stream-json。

逐条工具结果压缩通过独立的 `executionObservation` 保留有界进程/自检事实，
不再让失败原因提示挤掉退出码或检查结论。该字段只从结构化 Runtime 元数据投影，
不解析诊断文字；Message/Turn 历史转换保留它。Microcompact 单独压缩诊断正文，
完整保留最多 32 个步骤的退出码及原始观察步骤数，并继续说明这些事实不代表任务验收。
未知字段、命令内容和审计引用不会进入此投影。已删除的历史消息以及模型生成的整体
摘要仍可能丢失信息；本机制不承诺保存无限历史，也不把历史检查当作当前产物有效性证明。


## 完成与证据新鲜度

同一路径采用最新指纹；后续删除或缺少 hash 不继承旧存在状态/hash。Host 提供的
artifact 列表必须是当前快照。命令采用同一 `commandRef` 的最新记录，可通过
`CompletionCommandEvidence.artifacts` 绑定输入的存在状态/hash（存在的输入必须有 hash）；输入变化或缺少
当前观察后，这条验证不再有效。普通 shell 的目录写入不能自动提供逐文件证据，
Host 应在有明确交付要求时获取当前快照。

只有用户/Host 明确声明的 `CompletionContract` 才触发交付判断。共享 Runtime 在
预算允许时至多请求一次针对缺失产物/检查的继续执行，approval、取消及基础设施失败
不会变成要求模型绕过限制的提示。无合约的会话仍保留原自然结束语义。
Headless Host 可传入 `harnessPolicy` 和 `completionEvidence`；返回的 `completion`
独立展示交付证据；CLI 延续共享 Runtime 的 `incomplete` 停止原因和退出码约定。
外部评测结果仍由外部 verifier 独立报告。
