# Shell 审批目录事实与候选风险识别

## 状态与目标

本文记录审批与执行的目录事实及风险识别边界。它解决的是审批与执行的目录错位，
不增加 Agent 的任务流程、完成条件或 Bench 专用规则。

执行器和审批层必须针对同一工作区作出判断。字符串相同不代表操作对象相同；
反过来，相对路径与绝对路径指向同一个工作区子项时，也不应仅因写法不同而改变决策。

## 已复现的问题

- 原危险命令正则把所有绝对路径都视为广泛目标，却漏掉第二个操作数、分离选项和目录切换。
- 隔离子 Agent 的 registry 和 executor 已绑定子工作区，但审批回调闭包仍使用父工作区。
  决策测试复现了子工作区的绝对路径被拒绝、父工作区路径被当作允许目标的问题。
- 候选识别器最初把 `cd` 的失败分支带入 `&&` 右侧，误拦普通目录往返；随后又发现
  符号链接下逻辑 `cd ..` 与物理父目录混淆导致漏判。这两项均有失败日志与修复后的回归测试。

## 可信上下文

`ApprovalCallback` 新增可选第四参数 `ApprovalContext`，包含只读 `cwd` 和
`workspaceRoot`，以及 broker 提供的只读 `shell` 事实。执行器从自身配置和实际后端路由
构造并冻结该对象，不从模型参数读取这些事实。
子 Agent 审批包装器完整转发上下文。原有三个参数的回调仍可使用。

Headless 与 TUI 的危险 Shell 检查使用该上下文；直接调用审批函数而没有执行器上下文时，
保留宿主目录作为默认值。工具的显式 `args.cwd` 仍按执行器默认目录解析，不能改变工作区根。
这里描述的是危险命令检查，其他已有权限规则并未因此全部变成子工作区专属规则。

broker 的可选 `shellEnvironment` 方法描述语法与文件系统命名空间，不能授予权限。
本地启动器报告宿主 POSIX 或 Windows cmd；自定义启动器未声明时报告未知。
透明 broker 使用与执行相同的路由函数，按可信工具位置选择本地或 VM 事实。
VM 与云端适配器报告 POSIX 和 guest `/workspace`，不因为当前宿主是 Windows 而采用 cmd 语法。

## 候选识别器的职责

对于能识别的递归删除和放开所有人写权限的操作，检查全部目标、初始目录、直接目录切换和
符号链接。结构化检查的每一步从独立初始目录开始。普通 `echo`、`printf` 的字面量参数是数据。
`cd` 默认保留逻辑路径，`-P` 使用物理路径；文件操作数按文件系统实际路径解析。

上述实际路径解析只适用于本地 POSIX 环境。VM 初始目录复用实际启动器的 host-to-guest
映射函数；其目标仅做 guest POSIX 词法检查，绝不读取宿主同名路径的 `realpath`。
guest 符号链接的真实目标仍由执行边界约束，词法结果不证明 guest 内部路径隔离。
Windows cmd 与未知后端保留已有静态风险信号，不启动新增的 POSIX 目录模拟。
这不新增完整的 cmd/PowerShell 命令识别能力。

识别器返回空值只表示没有识别到风险，不能成为授权或隔离证明。它不是完整 Shell 解释器，
不执行变量或命令替换，也不能识别任意 Python、脚本、函数、别名或自定义程序的实际效果。
权限规则仍由宿主决定，实际文件与进程边界由 execution broker 和 OS/VM 执行。

策略优先级沿用现有契约：命中危险模式时 TUI 提示确认，Headless 拒绝，不能通过
`bypassPermissions` 或普通 allow 规则跳过。这里只对识别出的模式生效，不能将“不理解的
任意程序”一概等同于危险命令。改变这些授权语义需要单独的策略设计与测试，不能隐藏在路径修复中。

### Heredoc 输入与外层状态

识别器曾把 heredoc 正文直接并入外层 Shell 的目录和括号状态。例如，Python 输入中的
括号或文本中的 `cd /` 会使后续 `rm -rf cache` 被误判为工作区外删除。
现在先按重定向顺序分离正文，再从所属命令的目录状态副本进行保守风险扫描；正文的
目录变化和括号栈不回写外层。头部同一行上的后续 `cd` 也不能倒过来改变正文的初始目录。
递归分析保留逻辑目录拼写及未知目录状态，避免重新解析符号链接时丢失逻辑 `cd ..` 的语义。

正文仍可能是交给 Shell 的脚本或含有命令替换，因此不能简单忽略其危险命令。
这不是针对任意消费者的数据/代码判定：正文内的字面量危险操作仍可能被保守识别。
支持引号或反斜杠转义的分隔符、多个 heredoc、`<<-` 的前导 tab，以及头部注释。
未闭合正文、未支持的非引号反斜杠续行和超过八层的嵌套，保留原保守扫描，不能静默丢弃输入。
该变更不执行正文、不改写交给执行器的命令、不放宽权限，也不改变 cmd/未知后端的识别路径。

## 验证范围

1. 本地审批矩阵：全部操作数、选项顺序、引号、目录切换、符号链接、普通字面量数据与结构化步骤。
2. 真实 executor 和隔离子 Agent 调用链：可信上下文必须穿过包装器，绝不能由工具参数伪造。
3. 全量 Bun 测试、类型检查、CLI 构建及 macOS/Linux 实际路径探针。
4. VM 适配测试核对可信路由、guest 词法目标与实际提交 cwd。RecordingClient 只记录提交，
   不执行破坏性命令；真实 mTLS/VM 测试仍按已有环境配置跳过，不能声称完成真实 VM 验收。
5. Windows 路由及静态风险信号由单元测试覆盖；未执行真实 Windows 验收，不声称获得完整
   Windows 风险识别能力。新增 POSIX 文件系统分析不会用于 cmd。
6. 误拦与授权回归：普通字面量、目录往返及已知工作区子项放行到后续权限规则，
   危险模式、显式拒绝和 plan 模式保留原有优先级。识别不到风险不代表自动授权。
7. 固定最新可交付源码和二进制后，按原任务、模型、预算重新运行完整样本并审查每次结果。
8. Heredoc 决策矩阵覆盖正文状态隔离、多个/嵌套正文、命令替换、实际脚本危险操作、
   后续越界目标，以及逻辑/物理符号链接目录；分类测试不执行任何破坏性命令。

## 本轮 Bench 反思

冻结版本 `54cf1e24` 的五题样本已完成全部轨迹和官方验收审查：四题通过，一题输出错误，
五题 verifier 均执行。这不包含后续目录修复和本候选，也不是完整 Terminal-Bench 数据集结果。
逐次运行与哈希绑定证据保存在仓库外的 `zap-benchmark-results/harness-stream-continuation-20261015`。

失败轨迹没有观察到 Provider 中断、工具配对缺失或预算强制终止，模型在自己的输出异常时
作出了缺少证据的成功判断。通过轨迹也出现管道末端退出成功、前面的测试实际失败的情况；
该次模型读懂输出并继续修复。下一项能力工作应改善验证证据的表达和结论校准，
区分命令退出、行为验证、未证实假设与长期记忆。不得通过题目提示、隐藏测试反馈、
自动改写 Shell 语义或强制外部验收后才能退出，来制造得分提升。
